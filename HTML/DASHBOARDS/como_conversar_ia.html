1

Contexto: por que ele muda completamente o resultado

A IA responde melhor quando entende o cenário, o público e o estado atual do trabalho.

O contexto mínimo

  • Qual projeto está sendo trabalhado.
  • O que já existe e está aprovado.
  • Quem utilizará o resultado.
  • Qual problema precisa ser resolvido agora.
  • Quais regras o projeto já tem (CLAUDE.md).

Atividade

Escolha uma tarefa do FastPousada (ex.: o browse de Hóspedes) e descreva em quatro linhas: projeto, situação atual, usuário e resultado esperado. Compare a resposta com a de um pedido sem contexto.

EXEMPLO
Estou trabalhando no browse de Hóspedes do FastPousada, que usa SQLite pela FacilApp API SQL (porta 7777). A tela já segue o padrão visual aprovado do browse de Usuários. Corrija somente a exportação CSV, preservando o restante da tela. O CSV deve abrir no Excel mantendo os acentos.
2

Estrutura de um bom pedido

Uma fórmula simples reduz interpretações erradas e retrabalho.

A FÓRMULA
ObjetivoO que deve ficar pronto
RegraO que deve ser respeitado
DadosQuais informações usar
VisualComo apresentar
LimiteO que não alterar

Pedido verificável

Inclua uma condição que possa ser testada: “clique no botão”, “compile em Release”, “compare em 1280 × 768” ou “confirme o código HTTP”.

Atividade

Reescreva “faça uma tela de hóspedes” usando os cinco elementos. Termine dizendo como a entrega deverá ser testada.

MODELO REUTILIZÁVEL
Objetivo: browse de Hóspedes do FastPousada listando nome, documento, telefone e cidade.
Regras: mesmo padrão do browse de Usuários; cores só pelas variáveis --fa-*; dados só pela FacilApp API SQL.
Dados: tabela HOSPEDES no SQLite (porta 7777); exemplo: Maria Souza, CPF 123.456.789-09, (11) 98888-7777, Santos.
Visual: cabeçalho de 35px, linhas de 22px, busca à esquerda e botões à direita.
Limites: não alterar o index.html, o menu nem a tela de Usuários.
Validação: incluir, alterar e excluir um hóspede e conferir no Swagger (GET) que o registro mudou.
3

Revisão, ajustes e correção das respostas

Uma boa continuação aproveita o trabalho feito e aponta exatamente o desvio.

Como revisar

  1. Diga o que ficou correto.
  2. Aponte o erro observável.
  3. Informe a referência correta.
  4. Peça uma mudança limitada.
  5. Solicite novo teste.

Evite

  • Repetir toda a tarefa sem explicar o erro.
  • Mudar várias decisões ao mesmo tempo.
  • Dizer apenas “não funcionou”.
  • Aprovar antes de testar o resultado real.
EXEMPLO DE CONTINUAÇÃO
O modal abriu e o cadastro foi preservado. Falta somente centralizar os dados verticalmente nas linhas da grade. Use a mesma altura e tipografia do browse de Usuários. Não altere os botões nem o cabeçalho. Depois clique em dois registros e confirme que apenas uma linha permanece selecionada.
4

Biblioteca pessoal de prompts

Prompts úteis devem ser encontrados, adaptados e melhorados com facilidade.

Organização recomendada

  • Diagnóstico: localizar causa sem alterar código.
  • Implementação: criar ou corrigir uma função.
  • Revisão: conferir segurança, visual e regressões.
  • Entrega: compilar, testar e empacotar.

O que guardar

Nome, finalidade, entradas necessárias, prompt-base, exemplo de uso, validação esperada e histórico das melhorias que realmente deram resultado.

FICHA DE PROMPT
Nome: Corrigir browse de Hóspedes sem regressão
Finalidade: Ajustar uma função do browse preservando a tela aprovada
Entradas: hospedes.html, erro observado, referência visual (browse de Usuários) e teste
Prompt-base: No browse de Hóspedes do FastPousada, corrija somente [o problema observado]. Preserve cabeçalho,
  botões e a grade. Use a FacilApp API SQL (porta 7777). Depois clique em dois hóspedes e confirme o resultado.
Validação: abrir a tela, clicar nos controles e registrar o resultado
5

Backend: instalar a FacilApp API SQL e usá-la para conferir o trabalho

O prompt orienta o trabalho; a API, o Swagger e os testes fornecem dados verificáveis. A API não gera prompts: quem escreve o pedido é você, com o Claude Code.

Fluxo seguro

  1. Instalar o serviço FacilAppCursoSqlite e conferir GET /status na porta 7777.
  2. Autenticar pelo endpoint público de login.
  3. Guardar o Bearer somente na sessão necessária.
  4. Consultar o contrato no Swagger.
  5. Executar a função com dados controlados.
  6. Validar resposta e efeito no banco.

Responsabilidades

A IA não deve inventar endpoints nem expor senhas. Informe a URL da API, o contrato disponível e o objetivo; mantenha segredos no servidor e use o Bearer nas operações protegidas.

EXEMPLO INTEGRADO
Use o Swagger da FacilApp API SQL (http://127.0.0.1:7777/swagger) como contrato. Faça login com o usuário de testes do curso, guarde o accessToken apenas em memória e consulte GET /api/menu. Não registre senha nem Bearer. Mostre o código HTTP, a quantidade de registros e qualquer erro operacional.

Projeto final do módulo

Escolha uma rotina do FastPousada, escreva o prompt completo para o Claude Code, execute-a contra a API de teste e revise o pedido até obter um resultado comprovado.
