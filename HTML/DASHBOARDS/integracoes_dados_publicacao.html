Uso de API como ponte de integração

A interface pede uma operação; a API autentica, valida, consulta os dados e devolve uma resposta previsível.

TelaEnvia a solicitação
HTTP + JSONTransporta os dados
APIAutentica e valida
BancoExecuta a operação
RespostaRetorna resultado ou erro

Por que usar uma API

  • Evita colocar senha do banco no HTML.
  • Centraliza regras e validações.
  • Permite várias interfaces sobre os mesmos dados.
  • Documenta o contrato no Swagger.
  • Facilita logs, testes e manutenção.

Integrações do ecossistema

  • Impressão térmica ESC/POS: ficha de check-in e recibo na impressora da recepção.
  • Cloudflare: domínio, HTTPS e proteção na frente do servidor.

FacilApp API SQL

Serve autenticação, usuários, menus e operações SQL; no curso roda em http://127.0.0.1:7777 com SQLite. O cliente faz login, recebe um Bearer e usa esse token nas chamadas protegidas, sem conhecer as credenciais internas do banco.

Atividade

Desenhe o caminho de uma consulta desde o clique na tela até o retorno dos dados. Marque onde ficam autenticação, validação, SQL e mensagem de erro.

Regra de segurança

Tokens, senhas e segredos ficam protegidos. Nunca grave segredo no HTML, no JavaScript público, em URL, captura de tela ou log.

PROMPT DE INTEGRAÇÃO
Crie o fluxo de integração das reservas do FastPousada. A tela reservas.html deve chamar a FacilApp API SQL
(http://127.0.0.1:7777) por HTTP e JSON. Separe interface, autenticação Bearer, validação (datas e quarto livre),
regra de negócio, acesso ao SQLite, resposta e tratamento de erro. Não exponha credenciais do banco na tela.

Quando usar cada ferramenta

A escolha correta depende do local de uso, da conectividade, dos dispositivos e da forma de publicação.

DesktopImpressoras, arquivos, dispositivos e integração forte com Windows.
WebAcesso por navegador e atualização centralizada.
Rede localOperação interna com baixa latência e controle do servidor.
DadosAPI e banco como núcleo compartilhado.
PublicaçãoHTTPS, domínio, proxy, firewall e monitoramento.

Perguntas antes de decidir

  • Quem usa e em qual dispositivo?
  • Precisa funcionar sem internet?
  • Há impressoras ou equipamentos locais?
  • Quantos usuários simultâneos?
  • Quem fará instalação e atualização?

Combinação comum

No FastPousada, a FacilApp API SQL atende o sistema da recepção (desktop), o painel web do gerente e a tela de check-in no celular. Cada interface muda, mas dados e regras permanecem comuns.

Atividade

Escolha um projeto e monte uma matriz com público, dispositivo, rede, dados, implantação, atualização e risco. Só depois selecione a plataforma.

Evite

Não escolha tecnologia apenas por popularidade. Considere o que já existe, o custo da migração, as habilidades da equipe e os requisitos reais.

3

SQLite, SQL Server e PostgreSQL

Os três bancos da FacilApp API SQL: todos guardam os mesmos dados, mas diferem em administração, recursos, custos e dialeto SQL.

SQLiteUm arquivo, sem servidor: o banco da porta 7777 nas aulas e em instalações pequenas.
SQL ServerExpress no Windows, para a pousada com rede local e vários computadores.
PostgreSQLProdução na nuvem, no Ubuntu, atrás do nginx.

O que comparar

  • Licença e custo operacional.
  • Backup, restauração e replicação.
  • Drivers disponíveis.
  • Concorrência e volume.
  • Equipe e ferramentas existentes.

Portabilidade exige cuidado

Tipos de dados, paginação, datas, funções, identidade automática e parâmetros variam. Use comandos parametrizados e isole o dialeto específico.

O QUE MUDA ENTRE OS BANCOS
                 SQLite                    SQL Server                         PostgreSQL
Limitar linhas   ... LIMIT 10              SELECT TOP (10) ...                ... LIMIT 10
Chave automática INTEGER PRIMARY KEY       INT IDENTITY(1,1)                  GENERATED BY DEFAULT AS IDENTITY
Data/hora atual  CURRENT_TIMESTAMP         SYSDATETIME()                      CURRENT_TIMESTAMP
Nulo             COALESCE(v,0)             ISNULL(v,0) ou COALESCE(v,0)       COALESCE(v,0)
Paginação        LIMIT 20 OFFSET 40        OFFSET 40 ROWS FETCH NEXT 20 ROWS  LIMIT 20 OFFSET 40
Upsert           ON CONFLICT DO UPDATE     MERGE (testar concorrência)        ON CONFLICT DO UPDATE

Atividade

Crie a tabela QUARTOS do FastPousada no SQLite e no SQL Server. Compare identidade, texto, decimal, data, booleano, paginação e parâmetros.

Onde entra o SQLite

SQLite é excelente para aulas, protótipos, aplicações locais e bases embarcadas. Não exige servidor, mas ainda precisa de backup e controle de concorrência. No FastPousada começamos no SQLite e a FacilApp API SQL evolui para SQL Server e PostgreSQL sem mudar as telas.

PROMPT DE PORTABILIDADE
Analise o SQL que lista os quartos livres do FastPousada entre duas datas, escrito para SQLite, e adapte para SQL
Server. Liste diferenças de tipos, identidade, datas, funções, paginação e parâmetros. Preserve o resultado e gere
dados de teste (5 quartos e 8 reservas) para comparar as duas versões.
4

Token, redes locais, testes, publicação e diagnóstico

Publicar não é apenas copiar arquivos: é garantir acesso, segurança, observabilidade e recuperação.

1. ServiçoA API está iniciada e ouvindo na porta correta?
2. RedeIP, DNS, rota, NAT e firewall permitem o acesso?
3. HTTPURL, método, cabeçalhos, CORS e HTTPS estão corretos?
4. AplicaçãoToken, escopo, JSON, SQL e parâmetros estão válidos?

Ciclo do token

  1. Login público recebe usuário e senha.
  2. A API valida o usuário.
  3. O retorno fornece access_token e validade.
  4. O cliente envia Authorization: Bearer.
  5. Quando expirar, o usuário reloga ou renova conforme o contrato.

Onde a FacilApp API SQL roda

  • Windows: serviço do Windows, instalado e atualizado por PowerShell.
  • Linux: Ubuntu (compatível com o .NET 10), com o nginx na frente fazendo o HTTPS e o proxy para a API.
  • O mesmo código C# no .NET 10 nos dois, versionado no Git.
  • Cloudflare na frente do domínio: DNS, HTTPS e cache. Publicou? Confira com um ?x=aleatório na URL.

Publicação responsável

  • Defina endereço e porta.
  • Use HTTPS em acesso externo.
  • Configure firewall e NAT conscientemente.
  • Teste de outra máquina e outra rede.
  • Mantenha logs sem segredos e plano de rollback.

Erros frequentes

  • Failed to fetch: serviço, rede, HTTPS ou CORS.
  • 401: Bearer ausente ou inválido.
  • 403: autenticado, mas sem permissão.
  • 404: rota ou endereço incorreto.
  • 500: falha interna que deve aparecer no log seguro.

Teste final

Faça login, copie somente o token para memória, execute uma consulta protegida e simule uma falha de endereço. Registre status HTTP, mensagem, hipótese e correção.

CHECKLIST DE DIAGNÓSTICO
1. Confirmar processo e porta da API.
2. Testar a raiz e o Swagger localmente.
3. Testar IP local a partir de outra máquina.
4. Conferir URL, método, JSON e cabeçalhos.
5. Fazer login e usar o Bearer retornado.
6. Registrar status HTTP e resposta, sem expor segredos.
7. Consultar o log do servidor.
8. Corrigir uma camada por vez e repetir o teste.
